# Первый пилот миграции Mamkin 1.x → 2.0

Дата: 2026-11-12. Проверены файловый переход и восстановление контекста в отдельном чате существующего проекта. Это scoped evidence, не принятие всего MVP и не сравнительная оценка эффективности. Приватные продуктовые файлы, backup и стенограммы сюда не копируются; наблюдения сверены через локальное read-only чтение и connected thread tools. Внешнему читателю они не предоставляют полностью воспроизводимого публичного fixture.

## Наблюдаемое

- Использовались процедура `7be2dfbcd2c84f0daa15925c09284f1aaf23aa82` и два skills из `08c6e05fa5bc2c90874159089c51ad962357f699`; hashes совпали. Это первая редакция процедуры, не обновлённые правила ниже.
- Отдельная локальная ветка и исходная продуктовая ветка сохранены. Все 95 путей итогового patch соответствовали карте: 81 удалённый процессный файл, 8 изменённых смешанных и 6 новых. Tracked state закоммичен и чистый.
- Родительская независимая сверка подтвердила неизменность 1241 сохраняемого tracked-файла. Шесть исходных untracked-файлов совпали с контрольными SHA-256, снятыми наблюдателем до patch. Резервная копия исходных 1330 tracked-файлов и шести untracked прошла roundtrip.
- Координатор реально выполнил 7 тестов планировщика и 3 выбранные продуктовые регрессии. Карта сохранила 108 check definitions и 127 rules; реальные команды и guards не ослаблены. Проверены synthetic hook inputs и отказ guarded recovery затереть новую правку; это не native клиентский reload.
- В отдельном новом чате пользователь дал нейтральный запрос с путями, без готовых продуктовых ответов. Новый чат прочитал источники, сверил checkout/HEAD/dirty и два skills, восстановил принятую базу с причиной, blocked/deferred состояния, устаревший pending и ещё не принятое предложение. Продуктовую работу/записи не начинал.
- Обнаружены противоречия старых release requirements с поздними отложениями и предлагаемой архитектурой. Они остались вопросами продукта, не были автоматически решены миграцией.

## Что пилот выявил

1. После успешного read-only старта текущие записи продолжали требовать «назначить writer». Первый вариант пользовательского запроса этого не разрешал; повторять такой барьер при обычной уже разрешённой передаче незачем.
2. Подготовленный старым координатором запрос содержал факты и ожидаемые ответы. Это нормально для рабочего продолжения, но не для независимого теста памяти. Тест был проведён отдельным нейтральным запросом; эти два назначения нельзя смешивать.
3. Несколько старых docs оставили pending после уже полученного пользовательского ответа. Последний факт сохранили в отчёте миграции и связали с entrypoints. Данные не потерялись, но одноразовый отчёт стал постоянным владельцем продукта — дальнейшие миграции должны обновлять подтверждённый факт у постоянного владельца с сохранением истории.
4. Осталась слишком широкая формулировка о закрытии всего подхода по неудаче одного контроля. Наблюдалась неудача конкретного опыта; более общее решение требует основания. Существующий контракт памяти не требует добавлять для этого новый процесс.

## Согласованная доработка процедуры

Обычную передачу готовит старый координатор; с явным разрешением использует thread tools для одного нового чата и одной отправки. Иначе выдаёт текст для копирования. Новый чат в первом ответе сверяет источники, принимает уже порученную координацию и обновляет существующий current owner. Следующий запрос может сразу быть продуктовым; scope/limits/deadlines сохраняются. Для разрешённых имён используется `👑` у нового и буквальный `[arhcive]` перед `👑` у старого; переименование не является архивированием или удалением worktree.

Подтверждённые продуктовые факты сохраняются у постоянных владельцев, предложения не превращаются в решения. Результаты файлов, восстановления контекста, передачи координации и проектных hooks фиксируются отдельно. Непроверенная загрузка hooks не является собственным runtime Mamkin и ограничивает только реальные зависимые действия.

## Границы и следующий контроль

Не проверены: автоматическая отправка старым координатором, новая передача за первый ответ с обновлением текущего owner, native hooks/trust/config reload, полный продуктовый цикл с выполнением и продолжением, сравнительная польза на тех же Markdown-данных, все ignored bytes/ACL/xattr и глобальные writers. Переименование выбранных чатов выполняется отдельно по прямому запросу пользователя, не задним числом засчитывается прежнему пилоту.

До следующего применения новая процедура имеет только статические проверки и read-only review, не новый behavioral pass. Старые результаты/отрицательные verdicts не пересчитываются. Skills, модели, permissions и runtime не меняются; полные модельные регрессии повторно не запускались. Legacy structural validator используется как узкая проверка структуры, не как проверка новой передачи. Публикация новой редакции требует собственной Git authority.
