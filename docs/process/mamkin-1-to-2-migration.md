# Разовый переход Mamkin 1.x → 2.0

Редакция: 2026-11-17. Добавлена приватная координация; этот вариант и многопроектная передача ещё не исполнялись. Результаты первого пилота 2026-11-12: файловая миграция и восстановление контекста отдельным чатом наблюдались; уточнённая передача за первый ответ ещё не исполнена. [Результаты и границы](../follow-ups/mamkin-2-migration-pilot-2026-11-12.md). По отдельному решению пользователя она поддерживает переход существующих проектов; это не третий обязательный skill и не новый runtime Mamkin 2.0. Обычная работа после перехода не требует чтения этого документа.

Продуктовый контракт: [Mamkin 2.0 v0.3](../project/mamkin-2-spec.md). Функциональное evidence и известные ограничения: [отчёт](../follow-ups/mamkin-2-v03/README.md). Успех миграции не означает доказанного выигрыша Mamkin или автоматического принятия всего MVP.

## Источник и границы

Проверенный источник **реализации** опубликован в `https://github.com/malamuth/mamkin-builder`, ветка `codex/mamkin-2`, commit `08c6e05fa5bc2c90874159089c51ad962357f699`. Для двух skills использовать полный commit, а не подвижный HEAD ветки. Mamkin 2.0 становится основной версией в `main`; этот переход не меняет проверенный pin реализации.

Источник **процедуры** — конкретный полный commit этой редакции файла: перед применением получить его из выбранного доступного Git ref, проверить файл и сохранить pin отдельно от реализации. [Первая опубликованная редакция](https://github.com/malamuth/mamkin-builder/blob/7be2dfbcd2c84f0daa15925c09284f1aaf23aa82/docs/process/mamkin-1-to-2-migration.md) в `7be2dfbcd2c84f0daa15925c09284f1aaf23aa82` использована в пилоте, но не содержит уточнений передачи ниже. Не выдавать новую редакцию за старый pin. Если пользователь дал точный pin, читать его; смену согласованных правил не прятать под той же ссылкой. В implementation commit `08c6e05` процедуры нет. Далее читать Git objects по обоим pins, не изменяемый working tree источника. Неподтверждённый/недоступный источник оставляет подготовку read-only.

Из commit реализации в проект переносятся только:

| Путь | SHA-256 содержимого |
| --- | --- |
| `.agents/skills/mamkin-setup/SKILL.md` | `5257a195fe5f4537b1c1248000a2bd5fa0380c6473c40d746572d89d54475238` |
| `.agents/skills/mamkin-work/SKILL.md` | `df65fb77aaf43ee856d6ea7c7d7c31b8868de841afb0a7f621d261cfb45cb762` |

Перед применением сверить Git commit и фактические hashes; несовпадение останавливает перенос. Не копировать поверх проекта весь репозиторий, старые config/hooks/roles, `.mamkin`, `.git`, remotes или development evals. Не использовать старый template-sync/adopt/init для установки 2.0: они предназначены для другого слоя и могут вернуть 1.x.

Миграция конкретного репозитория выполняется в его собственном пользовательском чате с явно заданными checkout, задачей и Git authority. Этот документ не разрешает менять соседние репозитории, глобальные настройки, доступы или production. Обратимые изменения внутри уже разрешённого проектного плана не требуют повторного согласования каждого файла. Неоднозначное владение или изменение настоящих ограничений требуют отдельного решения по существующим правилам проекта.

## Контекст чата и worktree — разные вопросы

Для обычной работы 2.0 отдельные context-audit/reset/rollover skills и периодические ритуалы не требуются. Уже нужны актуальные `project.md`/`work.md` и сверка с источниками.

Если чат теряет исправления, повторно открывает отвергнутые решения без нового основания или не может объяснить следующий шаг:

1. Коротко перечитать релевантные текущие источники и сверить рабочую копию. Никакого обязательного audit packet или шкалы процентов контекста.
2. Сохранить текущую задачу, причины, результат/проверку, blocker и следующий шаг в существующих владельцах. Не дописывать стенограмму.
3. При продолжающейся путанице перейти в новый чат из этих файлов. Обычная длина чата сама по себе не является диагнозом. В CLI доступен штатный `/compact`, но сжатие не доказывает удаления старой методологии из контекста. [Официальные команды Codex](https://learn.chatgpt.com/docs/developer-commands?surface=cli).

Большой/грязный worktree требует разбираться с изменениями и их владельцами. Новый чат не уменьшает diff, не собирает потерянные worker results и не интегрирует ветки. Сначала определить незавершённые задачи и живых writers, сохранить состояние, затем завершить или безопасно разделить работу. Нельзя делать clean через reset/clean/discard/stash без применимой authority. Новый worktree нужен для изоляции конкретного писателя, а не как автоматическое лечение контекста.

Предпочтителен устойчивый control checkout, доступный следующему чату. Это способ организации проекта, не требование создать новый постоянный worktree. Для новой сессии всегда проверить фактический путь, branch, HEAD и dirty bytes; выбор проекта в UI не доказывает выбор нужного checkout.

## Минимальный результат перехода

При обычной repo-scoped установке в проекте остаются два Mamkin skills и два коротких входа `docs/mamkin/project.md`/`work.md`, а в AGENTS — команды/ограничения и навигация. Существующие project/domain skills, ADR, specs, backlog/roadmap, runbooks и evidence могут оставаться на прежних местах.

Один раз сохранить проектную запись миграции: исходное состояние и источник 2.0, точное сопоставление сохраняемых данных/владельцев, точные изменяемые/удаляемые пути, backup/recovery, проверки и передача координатору. Это временное evidence перехода, не новый постоянно обслуживаемый реестр или пакет для каждой задачи.

### Когда внутренняя координация должна оставаться приватной

Если продуктовый Git не должен содержать планы, coordination/QA/recovery и внутренние инструкции, сначала выбрать постоянного приватного владельца проектной памяти. Не возвращать туда старый overlay и не добавлять `.agents/skills/mamkin-*` или `docs/mamkin/*` в продуктовый commit только ради соответствия обычной раскладке. Если старого Mamkin в текущем продуктовом дереве уже нет, шаг удаления там не требуется.

- Использовать существующий разрешённый проектный private workspace либо явно согласованный приватный checkout. В нём держать два skills и короткие входы `project.md`/`work.md` (допустима обычная раскладка `docs/mamkin/`). Не нужен третий skill, обязательный отдельный репозиторий, реестр или новый runtime. У владельца должны быть понятные доступ, сохранность и способ продолжения в следующем чате; случайный `/tmp` не постоянная память.
- Пути к обоим `SKILL.md` и входам явно указать в приватном запросе продолжения. Если приватный каталог не входит в skill discovery текущего cwd, новый чат **читает указанные файлы явно**; не утверждать, что `$mamkin-work` автоматически обнаружен снаружи проекта. Проверить доступность чтения/разрешённой записи. Не устанавливать глобальные skills, не менять hooks/config/providers/trust для скрытой подгрузки. Отсутствие автоматического discovery не препятствует явному чтению.
- Отделить владельца памяти от владельца продукта: приватные входы ссылаются на актуальные продуктовые checkout/ветку/HEAD и постоянные источники; в продуктовых README/AGENTS, пакетах и публичной документации не должно появляться ссылок на приватную координацию. Для работы в продуктовом чате использовать приватный запрос продолжения, а не такой публичный указатель. Если чат работает из приватного coordination checkout, право писать продукт не следует из этого cwd: реализация остаётся отдельной разрешённой задачей в продуктовом репозитории.
- Публичные API/product docs, developer guidance, consumer skills и knowledge corpus остаются у своих владельцев. Их не удалять под именем «процесс», не заменять внутренним Mamkin и не переносить в private только из-за соседства с координацией. Сохранить ограничения разработчика, CI, permissions и границы публикации. Не изменять `.gitignore` как способ скрыть уже отслеживаемую внутреннюю информацию; не переписывать историю без отдельного разрешения.
- Передачу и recovery проверить для обоих слоёв: память/причины/IDs/межпроектные ссылки доступны новому чату, продуктовые bytes/refs и dirty/WIP сохранены, внутренние файлы/пути отсутствуют в предназначенном к публикации diff и пакетах. Если документировано, что продуктовый слой должен остаться неизменным, сверить это по факту. Резервная копия только продуктового Git не сохраняет внешнюю приватную память.

Сохранить выбранные точные пути в существующей приватной текущей записи и запросе продолжения. Миграция и последующие ответы работают с этим владельцем; не создавать параллельные текущие статусы в продукте. Разрешение на приватную память не является правом скопировать туда секреты, менять global/user layers или писать в соседние репозитории.

## 1. Снять фактическое состояние и остановить конфликтующих writers

Прочитать текущие инструкции, `pwd`, `git status --short --branch`, HEAD, remotes, связанные worktrees и источники незавершённых задач. Найти active/blocked/parked работы, незабранные worker packets, внешние операции и действующего владельца записи в каждом checkout.

На время смены процесса не запускать новые workers. Известные текущие записи завершить или безопасно приостановить; не прерывать неизвестный deploy/миграцию/платный запуск вслепую. Для продолжающегося worker нужен отдельный непересекающийся ownership и понятный сбор результата новым владельцем. Иначе переход этого checkout ждёт безопасной границы.

Dirty состояние допустимо, если известны владельцы и проверенное восстановление. Сохранить исходный Git commit и нужные uncommitted/untracked данные; commit сам по себе не сохраняет их. Нужные ignored-файлы остаются на месте либо сохраняются по явно разрешённому локальному защищённому пути. Не печатать секреты и не добавлять их в Git или публичный архив. Не предполагать, что новый worktree автоматически перенесёт все нужные локальные файлы: [официальное описание worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees).

Нужен проверяемый recovery path, а не только список dirty имён. Выбор snapshot/локального сохранения зависит от проекта; не устанавливать tooling. Не смешивать миграционный commit с чужими product-hunks и не делать массовый `git add .`. Если безопасно выделить изменения нельзя, подготовка остаётся read-only до разрешения конкретного конфликта.

## 2. Классифицировать по содержимому и использованиям

Старый `.mamkin/process-manifest.json` полезен как подсказка происхождения, но не является разрешением удалить совпавшие glob-пути. Проект мог изменить template-owned файл. Найти ссылки из AGENTS/overrides, hooks, CI, команд, specs и актуальных задач до удаления.

| Что найдено | Действие |
| --- | --- |
| `docs/project/brief.md`, project goals/constraints | Сохранить и связать с `project.md`; не заменять шаблоном |
| `docs/project/decision-log.md`, ADR и причины решений | Сохранить действующее и superseded с причинами; `project.md` указывает владельца |
| `features/00-roadmap.md`, backlog и feature specs | Сохранить цели, IDs, зависимости, приоритеты, gates, критерии и current state; `work.md` может ссылаться на существующий план |
| Walkthroughs, bug reports, owner acceptance, follow-ups и продуктовые runbooks | Это проектное знание/evidence. Сохранить нужное и не объявлять процессным мусором по имени каталога |
| Чистые руководства ролей, relay/handoff templates, model-routing, старые init/sync/context skills | Кандидаты на удаление из активного дерева после извлечения project facts и проверки ссылок |
| Смешанные `AGENTS.md`, README, config, naming/orchestration docs | Выделить реальные команды/ограничения/решения, затем удалить только старые процессные части |
| `.agents/skills/mamkin-*`, `.codex/agents/mamkin-*.toml` | Проверить каждый путь; убрать прежние процессные skills/roles, оставить новые два и сохранить project-specific знания из кастомизаций. Domain skills не удалять |
| `.mamkin` metadata, validation map, ledgers и source maps | Сначала извлечь stack/check commands, approvals, незавершённые работы, ownership и recovery. Удалять только исчерпанные process records, не действующие ссылки/данные |
| Process scripts/tests/evals/CI | Удалять вместе с проверенными чисто процессными зависимостями; сохранить реальные продуктовые проверки и обновить команды/CI, которые на них опирались |
| `.codex` permissions/rules, защитные hooks, formatting | Проверить отдельно. Переход не разрешает ослаблять реальные ограничения или молча отключать принятую проверку |

Например, в исходном 1.x `secret_scan.py` защищает от вывода секретов, `mamkin.rules` содержит prompt/forbidden boundaries, `post_edit_format.py` исполняет проектный formatter из validation map. Даже Stop-hook содержит напоминания о секретах/config, помимо ритуала closeout. Название Mamkin и template ownership недостаточны для удаления: сохранить guard/approved formatter как проектную настройку либо отдельно определить равноценную замену и authority. В 2.0 они не становятся обязательной поставкой.

Не удалять `.codex/config.toml` целиком. Сохранить применимые sandbox/approval/network/env policies, реальные native limits, команды и пользовательские предпочтения. Удаляется только ненужная маршрутизация/зависимость от старых ролей. Текстовое обещание в AGENTS не считается автоматически эквивалентом runtime-guard. Глобальные user/system настройки, providers, MCP, trust и credentials здесь не меняются.

## 3. Сохранить семантику backlog/roadmap/решений

Сплошная перепаковка в новый формат не требуется. Сначала выбрать одного текущего владельца каждого факта. Существующий подходящий Markdown остаётся владельцем; entrypoints содержат ссылки. Нормализация нужна лишь для неоднозначностей, мешающих выбору и продолжению.

Сверить актуальные сообщения пользователя с текущими владельцами: «сохранить документы» не значит заморозить устаревшее pending. Явный новый результат или принятое решение с причиной записать у постоянного владельца, сохранив прежний срез как историю. Не создавать блок Latest product facts в отчёте миграции как единственный текущий источник продукта; в отчёте достаточно ссылки. Если прямой запрос запрещает менять конкретный источник, использовать `project.md`/`work.md` как единственного владельца нового факта со ссылкой на прежний срез и отметить это исключение. Не менять требования из-за предложения или неоднозначного отзыва. Неудача одного контроля не закрывает весь класс решений без основания.

Для каждой незавершённой работы сохранить ID/aliases, результат, критерии, статус, blocker/recovery, этап, зависимости/приоритет и фактическую проверку. Сохранить применимое разрешение, старый deadline и consumed limits; новый чат их не сбрасывает. Недостающий ID назначается при принятии задачи без перенумерации старых ссылок.

Старые статусы не переводятся одной механической таблицей:

| Старый смысл | Правило перехода |
| --- | --- |
| Planned/spec approved | Обычно queued; принятие требований не равно разрешению на выполнение или done |
| Implementing | Active при актуальном фактическом результате и понятном владельце |
| Blocked/parked/on hold | Сохранить реальную причину/условие возобновления. Явно отложенная работа не становится автоматически доступной queued-задачей |
| Ready for walkthrough, Track-ready, Merge-ready, Ready for Git closeout | Сверить реальные done criteria: обязательная оставшаяся приёмка/интеграция не исчезает. Локальная задача может быть done, только если её критерии выполнены; pending delivery сохраняется отдельно, когда существенна |
| Delivered | Сохранить историческое свидетельство; не выдавать устаревший packet за проверку текущего результата |
| Cancelled/superseded | Сохранить как историю/неактивную заметку с причиной и ссылкой на замену. Не превращать отмену в успешное выполнение зависимости |

Не смешивать одобрение спецификации, task status и факт delivery. Разрешение менять процесс не разрешает завершать продуктовые задачи, публиковать код проекта или обходить gates. Неизвестный статус/проверку отметить честно; текущие исходники и решения важнее старого summary.

Сохранить цели этапов и mandatory/optional разделение. Режим backlog/sequential/hybrid должен отражать реальный план; если порядок неоднозначен, получить существенное решение, не выдумывать его. Активные specs сохраняют требования; state можно вынести к выбранному владельцу со ссылкой вместо второго текущего статуса.

Решения сохраняют «что и почему», известные альтернативы и значимые условия пересмотра. Прежнее основание не стирается из-за принятия нового; неизвестная причина не достраивается. Обоснования могут находиться в продуктовых docs, walkthroughs и старых пакетах — извлечь важное до удаления процесса.

## 4. Применить обратимый process-only patch

По проверенному проектному плану разместить точные два skills и короткие entrypoints у выбранного владельца. При обычной установке свести AGENTS к полезной навигации/проектным ограничениям; при приватной координации не добавлять в продуктовый AGENTS внутренние ссылки или overlay. Удалить подтверждённо лишние 1.x файлы **из активного дерева** и все активные ссылки/запуски их процедур. Сохранить Git history или проверенный отдельный backup.

Не создавать архив старых `SKILL.md` внутри `.agents/skills` и старых AGENTS/overrides в местах активного instruction discovery. Прежние нормы должны остаться историей, а не вторым включённым процессом. Исторические ссылки могут сохраняться как явно неактивные evidence; их наличие не равно активной зависимости.

Нет blanket удаления `docs/process/**`, `.codex/**` или `.mamkin/**`. Конкретный список выводится из классификации и извлечения данных. Путь с неизвестным содержимым/владельцем остаётся до разбирательства, а не удаляется для красивого отчёта.

После patch проверить: все прежние work items сопоставлены с актуальной записью или историей, существенные причины и gates не потеряны, нет двух текущих статусов, ссылки и команды существуют, старые process entrypoints не вызываются. Проверить affected CI/hooks/config parse и нужные продуктовые команды. Не повторять полный product suite, если изменился только процесс и для него уже достаточно проверок; не объявлять unrun проверки пройденными.

## 5. Передать работу новому координатору

Для перехода 1.x→2.0 базовый вариант — новый **не-forked** чат после изменения источников. Старый координатор готовит стартовый запрос: это первое сообщение для продолжения работы, а не отдельный skill или обязательный тест памяти. Обычный запрос может содержать краткий контекст, причины, открытые вопросы и точные ссылки; источники в репозитории остаются авторитетными.

Codex собирает AGENTS при старте run/session, fork сохраняет transcript; config/hooks зависят от реально загруженных слоёв. [AGENTS discovery](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [new/fork](https://learn.chatgpt.com/docs/developer-commands?surface=cli), [config и hooks](https://learn.chatgpt.com/docs/config-file/config-advanced). Это основание выбора свежего контекста, не новый runtime Mamkin.

1. На безопасной границе старый координатор завершает подготовку и новые dispatch/записи. В постоянных источниках сохранены задачи, причины, ограничения, dirty recovery и незабранные результаты; стартовый запрос указывает реальные продуктовые checkout/branch/HEAD, пути приватного владельца и обоих skills (если выбран этот вариант), источники и применимый пользовательский scope.
2. Когда пользователь явно разрешил создание нового чата и передачу запроса, старый координатор использует доступные thread tools и отправляет его **один раз** в один новый non-forked чат нужного проекта/checkout. Для уже выбранного чата нужна явная authority отправить туда сообщение. Не создавать промежуточный проверочный чат и цепочку successors. Если инструментов или разрешения нет — выдать готовый текст для копирования; чтение этой процедуры само не даёт права создавать чаты или отправлять сообщения.
3. Пользователь может сразу поручить этому чату быть основным координатором. Тогда за **первый ответ** новый координатор сверяет источники и реальную рабочую копию, принимает координацию и в рамках того же запроса обновляет существующий `work.md`/владельца: старый — история/восстановление, новый — текущий, восстановление контекста проверено, оставшиеся неопределённости названы. Не заводить реестр и не требовать ещё одного «назначения writer». Если проверочный чат уже успешно выполнил сверку, использовать её при неизменном состоянии.
4. При корректном checkout, понятном ownership и отсутствии реального конфликта следующий пользовательский запрос может сразу быть продуктовым. Если конкретная задача уже делегирована в стартовом запросе, выполнять её после сверки только в исходных границах. Одна миграция/переименование не расширяет scope, permissions, limits или deadlines. При конфликте/другом checkout остановить только зависимую работу, не затереть новые изменения.
5. С явным разрешением на переименование новый чат получает `👑 <project> Coordinator - project coordination`, старый — префикс `[arhcive]` перед его `👑` (буквальное написание пользователя). Это переименование, **не фактическое архивирование**. Имена не доказывают правильный checkout или передачу владения. Успех сверки и завершение передачи имеют одного текущего владельца записи; старые receipts остаются историей, не вечным current pending.

Старый чат/worktree сохраняются, пока нужны для данных, незабранных результатов и восстановления. Реальное архивирование/удаление требует отдельного разрешения и проверки сохранности/живых зависимостей. Переименование не удаляет worktree. Сообщения прежним workers допустимы только при соответствующей authority.

Отдельная проверка памяти — опциональный eval: новому чату дать только пути и вопросы, без готовых продуктовых ответов, и запретить изменения/исполнение. Её не включать в обязательную передачу. Тестовый read-only grant сам не разрешает обновлять учёт или запускать продукт; пользователь может затем продолжить в том же проверенном чате без ещё одного rollover.

Если fresh chat недоступен, сохранить готовый запрос и честно назвать передачу ожидающей этого шага. Не объявлять перенос проверенным по same-thread summary. Активный глобальный 1.x workflow назвать с его источником, не менять global/user layers. Само наличие необязательного глобального skill не блокирует 2.0.

### Проекты с managed children или несколькими worktrees

До удаления ledgers/registry определить все незавершённые active/blocked/parked работы, старые/новые владельцы и recovery routes каждого репозитория. Нельзя схлопнуть их в один backlog с потерей IDs и доступа к результатам. Child repositories мигрируют в собственных авторизованных чатах; parent dispatch при переходе остаётся остановленным до согласования владельцев.

Для каждого связанного проекта отдельно определить актуальный продуктовый checkout, владельца плана/решений, приватную границу, domain skills, незабранные результаты и scope передачи. Старый PRIMARY, app cwd или исторический registry не подменяют эту сверку. Parent не пишет child repository: подготовка и изменения child выполняются его собственным авторизованным координатором. Не распространять разрешение на все соседние проекты по имени. Полная уборка старых worktrees не обязательна, когда нужные данные/ownership и recovery уже сохранены.

Переходные registry/packets сохраняются как проектное evidence столько, сколько они ещё нужны живым зависимостям. После передачи их управляющая роль снимается; новый portfolio runtime в 2.0 не создаётся. Как дальше вручную координировать связанные проекты, определяется проектным решением, а не автоматическим переносом старой иерархии.

## 6. Результат и восстановление

Фиксировать отдельно, без одного общего «активация pending»:

| Проверка | Достаточное свидетельство | Что оно не доказывает |
| --- | --- | --- |
| Файлы | Данные/причины/IDs/gates сопоставлены; skills по pin; process patch и guards проверены; dirty сохранён; recovery доступен для продукта и выбранной приватной памяти; приватные paths/payload не включены в public diff/package | Загрузку конфигурации клиентом или продолжение новым чатом |
| Контекст | Новый чат на верном checkout восстановил актуальное решение и причину, работу, blocker и scope по источникам; соблюл режим запроса | Сравнительную пользу, фактическое выполнение следующей продуктовой задачи |
| Координация | По пользовательскому поручению новый чат — текущий, старый — история; существующая текущая запись отражает завершение | Новые permissions, сброс limits/deadlines или автоматический merge/push |
| Проектные hooks/config | Наблюдаемая загрузка/работа нужного guard в клиенте, когда она действительно проверена | Её нельзя вывести из одного наличия файла, parsed config или нового названия чата |

Файлы + восстановление контекста + ясное владение завершают передачу Mamkin. Непроверенную загрузку hooks назвать отдельно. Сама по себе она не держит передачу в вечном pending и не требует собственного runtime Mamkin; действие, реально зависящее от непроверенного guard, остаётся ограниченным правилами проекта до проверки. Если файловые guards ослаблены или данные потеряны, это blocker файловой миграции, а не необязательное замечание.

Проверки первого пилота и непроверенные условия сохранены в [отчёте](../follow-ups/mamkin-2-migration-pilot-2026-11-12.md). Для другого проекта выбрать нужные проверки по его состоянию; отсутствие случая можно покрыть безопасным fixture, не выдавая симуляцию за реальное внешнее действие.

Для rollback использовать обратный миграционный patch/revert и исходный локальный snapshot **поверх проверки новых изменений**, без reset/clean, force-delete или затирки новых product данных. Rollback файлов сам по себе не возвращает авторитет старому координатору: явно выбрать одного writer и заново сверить actual sources/runtime. Восстановление guards и startup не выводить из одного успешного revert.

## Готовые запросы для проекта

### Подготовка и передача старым координатором

Перед отправкой заменить `<ПОЛНЫЙ_COMMIT_ЭТОЙ_ПРОЦЕДУРЫ>` на проверенный доступный Git commit с этой редакцией. Старый `7be2dfb` не включает новые правила. Следующий шаблон прямо разрешает создание одного чата, отправку и переименование; убрать эту строку, если нужен только текст для ручного открытия. В остальном он не разрешает сообщения другим людям/чатам или архивирование.

```text
Мигрируй этот репозиторий с Mamkin 1.x на 2.0 по процедуре из
malamuth/mamkin-builder, commit <ПОЛНЫЙ_COMMIT_ЭТОЙ_ПРОЦЕДУРЫ>,
файл docs/process/mamkin-1-to-2-migration.md.
Реализация двух skills: 08c6e05fa5bc2c90874159089c51ad962357f699.
Проверь оба pins; не используй старые init/adopt/sync.

Разрешаю обратимые локальные изменения процесса в отдельной feature branch
и локальные commits. Сохрани данные, причины, history, user changes и guards.
Актуализируй подтверждённые факты у постоянных владельцев; предложения
не превращай в решения. Не меняй продуктовый код и глобальные настройки,
не пушь и не работай в других репозиториях.

После проверки подготовь запрос продолжения, открой один новый non-forked
чат этого проекта на нужном checkout и передай запрос один раз. Разрешаю
переименовать новый с 👑 в начале, старый с [arhcive] перед 👑.
Назначаю новый чат основным координатором: за его первый ответ нужно
сверить состояние и обновить существующую текущую запись передачи.
Продуктовую работу пока не начинай; после первого ответа я дам задачу.
Не архивируй/удаляй чаты, worktrees или ветки. Если инструментов нет,
выдай готовый текст для ручного открытия и точно укажи оставшийся шаг.
```

### Запрос продолжения в новом чате

Старый координатор подставляет реальные пути, IDs и scope. Не передавать стенограмму, секреты или потерянное основание как выдуманный факт. Короткий подтверждённый контекст допустим; он не подменяет чтение источников.

```text
Продолжай как основной координатор проекта с Mamkin 2.0 по поручению
пользователя о передаче. Старый чат <id> завершил работу и остаётся историей.
Checkout <path>, branch <branch>, проверенный HEAD <full SHA>.
Источники: <продуктовый AGENTS.md>, <точные пути project.md/work.md>,
<путь записи миграции>. При приватной координации явно прочитай
<приватный mamkin-setup/SKILL.md> и <приватный mamkin-work/SKILL.md>:
автоматическое discovery вне cwd не предполагается. Приватные ссылки
не переносить в продуктовые README/AGENTS или публикуемые пакеты.
Последний контекст и границы: <коротко, со ссылками>.

За первый ответ проверь актуальные sources, pwd/branch/HEAD/dirty,
текущую задачу, причины, blockers и остатки работ. Новые изменения не затирай.
При успешной сверке обнови существующую текущую запись: этот чат основной,
старый — история, файловая миграция/восстановление контекста завершены;
непроверенные проектные hooks обозначь отдельно. Не требуй ещё одного
назначения и не создавай реестр, новый чат или обязательный packet.
Поддержи разрешённые имена: 👑 у нового, [arhcive] перед 👑 у старого.
Если имена уже верны, ничего повторно не переименовывай.

Продуктовый scope: <точный исходный grant либо пока без продуктовой работы>.
Сохрани исходные consumed limits/deadlines и реальные project gates.
После сверки и обновления коротко сообщи результат; следующий запрос
пользователя может сразу быть продуктовым. Непроверенный guard ограничивает
только зависящие от него действия; его работу не объявляй доказанной.
```

Для отдельного теста памяти заменить этот запрос нейтральными вопросами по источникам и явно запретить записи. Не требовать такого теста перед каждой передачей. Эти шаблоны — способ продолжения в уже разрешённом проекте, не расширение repo/Git/global authority. Два продуктовых skills и runtime этой доработкой не изменяются; новый вариант передачи требует проверки при следующем применении.
