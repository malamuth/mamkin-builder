# Разовый переход Mamkin 1.x → 2.0

Дата: 2026-11-12. Статус: подготовленная процедура, ещё не исполненная на реальном проекте. По отдельному решению пользователя она поддерживает переход существующих проектов; это не третий обязательный skill и не новый runtime Mamkin 2.0. Обычная работа после перехода не требует чтения этого документа.

Продуктовый контракт: [Mamkin 2.0 v0.3](../project/mamkin-2-spec.md). Функциональное evidence и известные ограничения: [отчёт](../follow-ups/mamkin-2-v03/README.md). Успех миграции не означает доказанного выигрыша Mamkin или автоматического принятия всего MVP.

Неоднозначное владение или изменение настоящих ограничений требуют отдельного решения по существующим правилам проекта.

## Контекст чата и worktree — разные вопросы

Для обычной работы 2.0 отдельные context-audit/reset/rollover skills и периодические ритуалы не требуются. Уже нужны актуальные `project.md`/`work.md` и сверка с источниками.

Если чат теряет исправления, повторно открывает отвергнутые решения без нового основания или не может объяснить следующий шаг:

1. Коротко перечитать релевантные текущие источники и сверить рабочую копию. Никакого обязательного audit packet или шкалы процентов контекста.
2. Сохранить текущую задачу, причины, результат/проверку, blocker и следующий шаг в существующих владельцах. Не дописывать стенограмму.
3. При продолжающейся путанице перейти в новый чат из этих файлов. Обычная длина чата сама по себе не является диагнозом. В CLI доступен штатный `/compact`, но сжатие не доказывает удаления старой методологии из контекста. [Официальные команды Codex](https://learn.chatgpt.com/docs/developer-commands?surface=cli).

Большой/грязный worktree требует разбираться с изменениями и их владельцами. Новый чат не уменьшает diff, не собирает потерянные worker results и не интегрирует ветки. Сначала определить незавершённые задачи и живых writers, сохранить состояние, затем завершить или безопасно разделить работу. Нельзя делать clean через reset/clean/discard/stash без применимой authority. Новый worktree нужен для изоляции конкретного писателя, а не как автоматическое лечение контекста.

Предпочтителен устойчивый control checkout, доступный следующему чату. Это способ организации проекта, не требование создать новый постоянный worktree. Для новой сессии всегда проверить фактический путь, branch, HEAD и dirty bytes; выбор проекта в UI не доказывает выбор нужного checkout.

## Минимальный результат перехода

В проекте остаются два Mamkin skills и два коротких входа `docs/mamkin/project.md`/`work.md`, а в AGENTS — команды/ограничения и навигация. Существующие project/domain skills, ADR, specs, backlog/roadmap, runbooks и evidence могут оставаться на прежних местах.

Один раз сохранить проектную запись миграции: исходное состояние и источник 2.0, точное сопоставление сохраняемых данных/владельцев, точные изменяемые/удаляемые пути, backup/recovery, проверки и передача координатору. Это временное evidence перехода, не новый постоянно обслуживаемый реестр или пакет для каждой задачи.

## 1. Снять фактическое состояние и остановить конфликтующих writers

Прочитать текущие инструкции, `pwd`, `git status --short --branch`, HEAD, remotes, связанные worktrees и источники незавершённых задач. Найти active/blocked/parked работы, незабранные worker packets, внешние операции и действующего владельца записи в каждом checkout.

На время смены процесса не запускать новые workers. Известные текущие записи завершить или безопасно приостановить; не прерывать неизвестный deploy/миграцию/платный запуск вслепую. Для продолжающегося worker нужен отдельный непересекающийся ownership и понятный сбор результата новым владельцем. Иначе переход этого checkout ждёт безопасной границы.

Dirty состояние допустимо, если известны владельцы и проверенное восстановление. Сохранить исходный Git commit и нужные uncommitted/untracked данные; commit сам по себе не сохраняет их. Нужные ignored-файлы остаются на месте либо сохраняются по явно разрешённому локальному защищённому пути. Не печатать секреты и не добавлять их в Git или публичный архив. Не предполагать, что новый worktree автоматически перенесёт все нужные локальные файлы: [официальное описание worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees).

Нужен проверяемый recovery path, а не только список dirty имён. Выбор snapshot/локального сохранения зависит от проекта; не устанавливать tooling. Не смешивать миграционный commit с чужими product-hunks и не делать массовый `git add .`. Если безопасно выделить изменения нельзя, подготовка остаётся read-only до разрешения конкретного конфликта.

## 2. Классифицировать по содержимому и использованиям

Старый `.mamkin/process-manifest.json` полезен как подсказка происхождения, но не является разрешением удалить совпавшие glob-пути. Проект мог изменить template-owned файл. Найти ссылки из AGENTS/overrides, hooks, CI, команд, specs и актуальных задач до удаления.

| Что найдено | Действие |
| --- | --- |
| `docs/project/brief.md`, project goals/constraints | Сохранить и связать с `project.md`; не заменять шаблоном |
| `docs/project/decision-log.md`, ADR и причины решений | Сохранить действующее и superseded с причинами; `project.md` указывает владельца |
| `features/00-roadmap.md`, backlog и feature specs | Сохранить цели, IDs, зависимости, приоритеты, gates, критерии и current state; `work.md` может ссылаться на существующий план |
| Walkthroughs, bug reports, owner acceptance, follow-ups и продуктовые runbooks | Это проектное знание/evidence. Сохранить нужное и не объявлять процессным мусором по имени каталога |
| Чистые руководства ролей, relay/handoff templates, model-routing, старые init/sync/context skills | Кандидаты на удаление из активного дерева после извлечения project facts и проверки ссылок |
| Смешанные `AGENTS.md`, README, config, naming/orchestration docs | Выделить реальные команды/ограничения/решения, затем удалить только старые процессные части |
| `.agents/skills/mamkin-*`, `.codex/agents/mamkin-*.toml` | Проверить каждый путь; убрать прежние процессные skills/roles, оставить новые два и сохранить project-specific знания из кастомизаций. Domain skills не удалять |
| `.mamkin` metadata, validation map, ledgers и source maps | Сначала извлечь stack/check commands, approvals, незавершённые работы, ownership и recovery. Удалять только исчерпанные process records, не действующие ссылки/данные |
| Process scripts/tests/evals/CI | Удалять вместе с проверенными чисто процессными зависимостями; сохранить реальные продуктовые проверки и обновить команды/CI, которые на них опирались |
| `.codex` permissions/rules, защитные hooks, formatting | Проверить отдельно. Переход не разрешает ослаблять реальные ограничения или молча отключать принятую проверку |

Например, в исходном 1.x `secret_scan.py` защищает от вывода секретов, `mamkin.rules` содержит prompt/forbidden boundaries, `post_edit_format.py` исполняет проектный formatter из validation map. Даже Stop-hook содержит напоминания о секретах/config, помимо ритуала closeout. Название Mamkin и template ownership недостаточны для удаления: сохранить guard/approved formatter как проектную настройку либо отдельно определить равноценную замену и authority. В 2.0 они не становятся обязательной поставкой.

Не удалять `.codex/config.toml` целиком. Сохранить применимые sandbox/approval/network/env policies, реальные native limits, команды и пользовательские предпочтения. Удаляется только ненужная маршрутизация/зависимость от старых ролей. Текстовое обещание в AGENTS не считается автоматически эквивалентом runtime-guard. Глобальные user/system настройки, providers, MCP, trust и credentials здесь не меняются.

## 3. Сохранить семантику backlog/roadmap/решений

Сплошная перепаковка в новый формат не требуется. Сначала выбрать одного текущего владельца каждого факта. Существующий подходящий Markdown остаётся владельцем; entrypoints содержат ссылки. Нормализация нужна лишь для неоднозначностей, мешающих выбору и продолжению.

Для каждой незавершённой работы сохранить ID/aliases, результат, критерии, статус, blocker/recovery, этап, зависимости/приоритет и фактическую проверку. Сохранить применимое разрешение, старый deadline и consumed limits; новый чат их не сбрасывает. Недостающий ID назначается при принятии задачи без перенумерации старых ссылок.

Старые статусы не переводятся одной механической таблицей:

| Старый смысл | Правило перехода |
| --- | --- |
| Planned/spec approved | Обычно queued; принятие требований не равно разрешению на выполнение или done |
| Implementing | Active при актуальном фактическом результате и понятном владельце |
| Blocked/parked/on hold | Сохранить реальную причину/условие возобновления. Явно отложенная работа не становится автоматически доступной queued-задачей |
| Ready for walkthrough, Track-ready, Merge-ready, Ready for Git closeout | Сверить реальные done criteria: обязательная оставшаяся приёмка/интеграция не исчезает. Локальная задача может быть done, только если её критерии выполнены; pending delivery сохраняется отдельно, когда существенна |
| Delivered | Сохранить историческое свидетельство; не выдавать устаревший packet за проверку текущего результата |
| Cancelled/superseded | Сохранить как историю/неактивную заметку с причиной и ссылкой на замену. Не превращать отмену в успешное выполнение зависимости |

Не смешивать одобрение спецификации, task status и факт delivery. Разрешение менять процесс не разрешает завершать продуктовые задачи, публиковать код проекта или обходить gates. Неизвестный статус/проверку отметить честно; текущие исходники и решения важнее старого summary.

Сохранить цели этапов и mandatory/optional разделение. Режим backlog/sequential/hybrid должен отражать реальный план; если порядок неоднозначен, получить существенное решение, не выдумывать его. Активные specs сохраняют требования; state можно вынести к выбранному владельцу со ссылкой вместо второго текущего статуса.

Решения сохраняют «что и почему», известные альтернативы и значимые условия пересмотра. Прежнее основание не стирается из-за принятия нового; неизвестная причина не достраивается. Обоснования могут находиться в продуктовых docs, walkthroughs и старых пакетах — извлечь важное до удаления процесса.

## 4. Применить обратимый process-only patch

По проверенному проектному плану установить точные два skills, подготовить короткие entrypoints и свести AGENTS к полезной навигации/проектным ограничениям. Удалить подтверждённо лишние 1.x файлы **из активного дерева** и все активные ссылки/запуски их процедур. Сохранить Git history или проверенный отдельный backup.

Не создавать архив старых `SKILL.md` внутри `.agents/skills` и старых AGENTS/overrides в местах активного instruction discovery. Прежние нормы должны остаться историей, а не вторым включённым процессом. Исторические ссылки могут сохраняться как явно неактивные evidence; их наличие не равно активной зависимости.

Нет blanket удаления `docs/process/**`, `.codex/**` или `.mamkin/**`. Конкретный список выводится из классификации и извлечения данных. Путь с неизвестным содержимым/владельцем остаётся до разбирательства, а не удаляется для красивого отчёта.

После patch проверить: все прежние work items сопоставлены с актуальной записью или историей, существенные причины и gates не потеряны, нет двух текущих статусов, ссылки и команды существуют, старые process entrypoints не вызываются. Проверить affected CI/hooks/config parse и нужные продуктовые команды. Не повторять полный product suite, если изменился только процесс и для него уже достаточно проверок; не объявлять unrun проверки пройденными.

## 5. Активировать процесс новым координатором

Для перехода 1.x→2.0 базовый вариант — **новый не-forked чат** после изменения источников. Прежний чат выполняет подготовку и сохраняет state; переинструкция в той же длинной истории — менее надёжное доказательство чистой активации.

Основание рекомендации: Codex собирает цепочку AGENTS при старте run/session, а fork сохраняет прежний transcript. Новый файл на диске не доказывает, что уже работающий контекст перестал использовать старое. Config/hooks также зависят от загруженных project/user layers. [AGENTS discovery](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [new/fork commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli), [project config и hooks](https://learn.chatgpt.com/docs/config-file/config-advanced).

Порядок передачи короткий, без нового постоянного протокола ролей:

1. Старый координатор прекращает новые записи/dispatch на безопасной границе и остаётся только владельцем подготовки/восстановления. Сохранены точные checkout/branch/HEAD, dirty recovery, текущие задачи/причины, grants и незабранные результаты.
2. Пользователь открывает или явно поручает открыть новый чат в **этом проекте и нужном checkout**. Сам запрос «подготовь миграцию» не создаёт новый чат и не рассылает сообщения. Старт — только чтение и сверка, без product execution.
3. Новый координатор читает текущие источники и называет путь/branch/HEAD, dirty boundary, активную задачу, актуальное решение с причиной, blocker, незавершённые workers и следующий разрешённый шаг. Проверить факты по файлам и инструментам; одной фразы «я работаю по 2.0» недостаточно.
4. После успешной сверки зафиксировать один источник записи: старый координатор retired/read-only, новый — текущий. Сбор прежних worker результатов остаётся определённым по их IDs; сообщения workers только при соответствующей authority. Product work возобновляется лишь в пределах применимого запроса, не от факта миграции.
5. Старый чат/worktree сохраняются, пока от них зависят данные, writers или восстановление. Архивирование/удаление — отдельное явно разрешённое действие после проверки сохранности, integration и живых зависимостей. Не архивировать чат ради смены имени, если это ставит под риск используемый worktree.

Если fresh chat/reload пока недоступен, завершить файлы и сохранить starter, но не выдавать same-thread summary за проверенную чистую активацию. Не плодить successors. Если активные global инструкции продолжают навязывать 1.x, назвать источник и нужную отдельную настройку; проектная миграция не разрешает редактировать user/system layers. Само наличие необязательного глобального skill не является блокером, пока он не выступает действующим процессом.

### Проекты с managed children или несколькими worktrees

До удаления ledgers/registry определить все незавершённые active/blocked/parked работы, старые/новые владельцы и recovery routes каждого репозитория. Нельзя схлопнуть их в один backlog с потерей IDs и доступа к результатам. Child repositories мигрируют в собственных авторизованных чатах; parent dispatch при переходе остаётся остановленным до согласования владельцев.

Переходные registry/packets сохраняются как проектное evidence столько, сколько они ещё нужны живым зависимостям. После передачи их управляющая роль снимается; новый portfolio runtime в 2.0 не создаётся. Как дальше вручную координировать связанные проекты, определяется проектным решением, а не автоматическим переносом старой иерархии.

## 6. Приёмка и восстановление

Миграция принята, когда одновременно:

- Все исходные задачи, roadmap gates, существенные решения/причины и unresolved ownership сопоставлены без потери; действующие источники однозначны.
- Два skills имеют ожидаемые bytes; нет активной зависимости от старого процесса или ослабления реальных ограничений.
- Изменения product code, secrets, remotes и пользовательского dirty состояния не присвоены миграции и не потеряны.
- Новый чат на правильном checkout восстанавливает состояние, объясняет «почему» и следующую задачу; read-only старт не начал продуктовую работу.
- Есть один текущий координатор, ясные маршруты незабранных результатов и проверенный recovery; retained chats/worktrees отмечены явно.

Проверки на первом проекте: действующий backlog/roadmap и причина выбора; решение и superseded причина; blocked задача/required acceptance; сохранение dirty bytes; one-off вопрос без карточки; два entrypoints без копий; закрытые gates и узкий grant. Отсутствующий случай можно проверить безопасным fixture, но нельзя объявить реальные внешние действия проверенными по симуляции.

Для rollback использовать обратный миграционный patch/revert и исходный локальный snapshot **поверх проверки новых изменений**, без reset/clean, force-delete или затирки новых product данных. Rollback файлов сам по себе не возвращает авторитет старому координатору: явно выбрать одного writer и заново сверить actual sources/runtime. Восстановление guards и startup не выводить из одного успешного revert.
