# Managed Projects

Use this optional protocol when one project coordinates independently owned child repositories. Single-project work needs no portfolio registry. `mamkin-coordinate` remains the entrypoint; context audit/reset and Git delivery keep their existing responsibilities.

## Authority And Records

The parent owns priorities, cross-project dependencies, coordinator identity and transfer decisions. Each child owns its product sources, implementation, acceptance, local Git delivery and task ledger. Parent instructions never extend write authority across repositories. Child file changes require an authorized task in that child's project context; the parent collects its result. Direct cross-task messages require explicit human authorization, including messages requesting a reset or transfer. Read/wait collection needs no send authorization.

When a requested child change is not yet authorized for dispatch, prepare the complete owning-project assignment in the parent first: named child/coordinator, exact sources and checkout, scope, acceptance, validation, return packet and gates. Present only the remaining launch/send authorization; do not edit the child or send the prepared assignment until that authority exists.

Initialize the parent's project-owned `docs/project/project-coordinators.json` from `docs/templates/project-coordinators.json`. Record the parent task and, per child: stable project id, app project context, owning repository, coordinator task, authority generation, status, exact last-confirmed worktree/branch/commit/dirty paths, source packet, child active-lane ledger and recovery owner. Use explicit `checkedAt` and evidence; the registry is last-confirmed routing state, never proof of live Git, tools or acceptance. Keep previous transfer packets as history rather than overwriting lineage.

Each managed project, including the parent when it dispatches work, maintains its own `docs/project/active-lanes.json` even for a single lane. Initialize an empty `lanes` array when no work is active. Record task id, owner, status, worktree, branch/commit, current packet and recovery owner before dispatch; reconcile after receipt, blocking, parking, supersession, transfer and completion. Keep completed/superseded rows as history. Bounded subagents stay inside their parent lane and are not durable task rows. The two-unresolved-track cap applies separately to independent tracks within each project; three child projects do not themselves consume three parent tracks. Shared external surfaces still require one declared writer or serialization.

Run the read-only structural checks:

```bash
python3 scripts/validate_coordination_contracts.py portfolio docs/project/project-coordinators.json
python3 scripts/validate_coordination_contracts.py lanes docs/project/active-lanes.json
```

The parent reads the exact child ledger and current owning packet before routing dependent work. A missing/unreadable ledger, conflicting coordinator identity or unconfirmed checkout blocks new dispatch to that child until reconciled. Do not infer completion from an idle chat or a clean worktree. Reset does not erase transcript history; rollover does not integrate Git or authorize cleanup.

## Parent-Led Coordinator Transfer

Use after human approval of the named child rollover, or an explicit standing delegation covering this operation. An audit may recommend transfer but cannot execute it. A child may request reset/rollover; the parent owns the portfolio switch. For a same-thread reset, collect the child's source-grounded reset packet and reconcile routing without changing its coordinator id/generation. The focused context skill owns the reset itself.

1. **Prepare:** stop admitting new child work. Finish or safely pause active mutations, paid/live runs and deployments before transfer; do not interrupt an unknown running operation. Mark the child `transitioning` while the old task remains the sole authority, restricted to transfer preparation and recovery. Create a project-owned transfer record from `docs/templates/coordinator-transfer.json`. The child saves a source-grounded reset packet in its owning repository, normally in a committed baseline under the declared local Git authority. If a committed baseline is required but unavailable, stop; never manufacture a clean state. Record exact checkout, commit, dirty paths and a SHA-256 of the saved packet. Preserve dirty bytes with a named durable snapshot and evidence in that packet; a path list alone cannot restore them. The packet names current decisions, process/model baseline, external operations, evidence limits, all unresolved tasks and next safe action.
2. **Start:** create one fresh, non-forked coordinator in the child's actual project context. Ordinary project creation may default to the primary checkout; explicitly verify/select the recorded worktree, branch and commit before any writes. Transfer does not require a new branch or worktree by itself. The starter includes parent identity, generation, exact packet/path/hash, child ledger and all newer human decisions. It authorizes only source reconciliation and a receipt. Creation requires human authorization; do not use a send tool implicitly.
3. **Verify:** collect the fresh task's first receipt with wait/read tools. It must name the child and its own task id, read current instructions and product sources, match packet hash and checkout baseline, reconcile dirty preservation and newer decisions, accept every active/blocked/parked lane by id, name blockers and state the next safe action. Validate the transfer record with `transfer`. JSON validation checks declared consistency only; independently inspect the actual receipt and source bytes. A copied summary or matching hash alone is insufficient. Any mismatch, missing receipt, unsafe live state or unresolved blocker leaves the old task authoritative and prevents promotion. Record `blocked`, retain both ids and use bounded recovery/manual relay. Never create repeated successors blindly.
4. **Promote:** retire the old task's dispatch authority and record its explicit stop acknowledgement; a renamed/stopped task may remain unarchived. Update the child registry to the new id and increment generation exactly once, then validate the promoted transfer against that registry. Reconcile each child ledger's owner/recovery route in an authorized child task. The new coordinator collects outstanding worker packets by exact task id; optional worker notification requires send authorization. Late packets to the old id remain recoverable evidence and are collected by the successor; they never reactivate the old coordinator. Resume only after registry, child ledger and receipt agree. This is a serialized checkpoint, not an atomic multi-repository transaction; failure during the switch leaves dispatch paused until one authority is restored.
5. **Retain or archive:** keep the old chat renamed/stopped until the separate cleanup preflight passes. Archiving can remove an associated managed worktree: never archive the old chat while that copy is used by the successor, any worker or an unfinished check. A successful promotion does not authorize archival, worktree removal, branch deletion or remote writes.

```bash
python3 scripts/validate_coordination_contracts.py transfer docs/project/coordinator-transfers/<id>.json
python3 scripts/validate_coordination_contracts.py transfer docs/project/coordinator-transfers/<id>.json --registry docs/project/project-coordinators.json
```

`promoted` requires the registry argument. Before promotion, a supplied registry must name the old task/generation and `transitioning` status; a blocked transfer may instead use `blocked`. `active` or `retired` is inconsistent with a paused transfer. The validator does not contact chats, execute commands in packets, inspect another repository or perform any switch. Mark the old task's title as retired with its successor id when title tools and authority are available. If tools are unavailable, return the exact starter/manual steps and keep the transfer blocked until receipt and retirement can be verified.

For `receipt-verified` and `promoted`, fill `receipt` with these exact fields: `task`, `projectId`, `worktree`, `branch`, `commit`, `packetSha256`, `acceptedLaneIds` (every unresolved id, no history rows), `blockers` (empty), `sourceReconciliation`, `nextSafeAction` and `evidence`. A dirty baseline also requires `baseline.dirtyPreservation` and `receipt.dirtyStateEvidence`. Promotion additionally fills `retirement.task`, `retirement.disposition` (`renamed-stopped` or `archived`) and `retirement.evidence`; `archived` must already have passed the separate cleanup gate. Archive failure does not undo valid authority transfer: retain the renamed/stopped task and report pending cleanup.

## Managed Parent Rollover

Carry the entire registry, authority generations, transfer history and unresolved child recovery ownership through the normal parent reset baseline. For a managed parent, successor receipt is mandatory, overriding the normal skill's optional receipt language. Keep parent dispatch paused until the fresh parent has reconciled every child identity, ledger and outstanding transfer from current sources and returned a source-grounded receipt. Missing/mismatched receipt leaves the old parent authoritative for recovery; do not retire it or resume dispatch.

After a verified receipt and old-parent stop acknowledgement, update `parent.coordinatorTask` to the successor and increment `parent.generation` once. Reconcile current registry `recoveryOwner` fields and parent/child ledger routes that name the outgoing parent through authorized owning tasks; preserve historical references and all child coordinator ids/generations. Validate the registry and confirm actual routes before the fresh parent resumes. Record receipt, old/new ids, generations, route reconciliation and retention/cleanup in the parent reset packet. An incomplete checkpoint stays paused; it never implicitly rolls over a child or changes its model/process.

## Task And Worktree Closeout

After acceptance, first finish or explicitly retain Git delivery under `git-delivery.md`. Collect the final packet and required evidence, then mark the task ledger complete/superseded and choose a resource disposition. Task completion, accepted integration, chat retirement and worktree cleanup are distinct states.

Before archiving a chat or removing a worktree, the owning coordinator performs a fresh preflight and saves `docs/project/lane-closeouts/<id>.json` from `docs/templates/lane-closeout.json`. Check exact task/worktree association, current Git status including untracked files, integration evidence (or justified no-Git work), pending packets, all live consumers including the successor, and preservation of evidence and needed ignored files. Inspect accepted commit reachability or the verified squash diff under Git delivery; clean status is insufficient. Both chat archive and worktree removal require explicit matching authority, no dirty paths, no live dependents, no uncollected packets, resolved integration and verified preservation. Store the closeout receipt outside a worktree being removed. Validator success is not fresh filesystem or integration proof.

```bash
python3 scripts/validate_coordination_contracts.py closeout docs/project/lane-closeouts/<id>.json
```

If any condition fails, record `retain` with the reason/recovery owner. Preserve the worktree, rename/retire the chat when safe, and finish later. Do not stash, reset, force-delete, prune or discard to make cleanup pass. Use managed app tools for supported managed resources and record snapshot/restore references; primary, pinned, shared, permanent or otherwise unsupported worktrees may need retention/manual handling. Recheck dependencies immediately before execution. A snapshot does not replace accepted integration or preserve ignored files automatically. Never auto-delete branches; that remains the separate Git delivery contract.

Record the actual archive/removal result, retained resources, recovery reference and final registry/ledger reconciliation in the coordinator final packet. An archive failure is retained state, not completed cleanup. No recurring monitor or automatic cleanup is installed by this protocol.
