# Mamkin 2.0 Спецификация MVP

Версия: 0.2. Дата: 2026-11-10.

Статус: спецификация для отдельной реализации. Создание этой записи не разрешает начинать реализацию.

План и критерии приёмки: [План MVP](mamkin-2-mvp-plan.md).

## Принятые решения

- Mamkin 2.0 — самостоятельная конструкция с минимальным ядром. Сохранять устройство и ритуалы Mamkin 1.x не требуется.
- Единственная поддерживаемая среда — Codex. Claude Code, другие среды и адаптеры исключены из продукта.
- MVP составляет весь запланированный объём. Отдельной дорожной карты после MVP нет. Исключённые возможности не считаются отложенными обязательствами.
- Разработка ведётся в существующем репозитории `mamkin-builder`, в ветке `codex/mamkin-2`. Новый репозиторий не нужен.
- В ветке разрешено заменить существующую структуру при последующей явно запрошенной реализации. Поддерживать две версии одновременно не требуется.
- Текущая задача сохраняет только спецификацию и план. Активные инструкции, skills, настройки, скрипты и реализация Mamkin 1.x остаются без изменений.

## Назначение

Mamkin 2.0 — небольшой слой управления проектной работой поверх Codex. Он помогает сохранять цель, выбирать следующую разрешённую задачу, получать проверяемый результат и продолжать работу после перерыва.

Основной пользователь ведёт проект вместе с агентом и хочет меньше повторять контекст, задавать порядок работы и контролировать существенные решения.

Минимальное ядро отвечает за четыре функции:

| Функция | Результат |
| --- | --- |
| Ориентация | Понятны цель, ограничения и актуальное состояние проекта |
| Выбор работы | Выбрана доступная задача в пределах разрешённого объёма |
| Выполнение и проверка | Получен результат, соответствующий критериям готовности |
| Продолжение | Новый запуск восстанавливает работу по текущим источникам |

Обычную задачу основной агент планирует, выполняет и проверяет самостоятельно. Дополнительная структура появляется только при конкретной необходимости.

## Объём продукта

В MVP входят:

- Минимальная настройка нового или существующего проекта в Codex.
- Два repo-scoped skills: настройка и выполнение/продолжение работы.
- Markdown как единственное хранилище состояния Mamkin 2.0.
- Одна задача, последовательные этапы, бэклог и их сочетание.
- Явные границы продолжения и условия остановки.
- Сохранение блокеров, важных решений и свидетельств проверки.
- Восстановление работы после перерыва или смены чата.
- Использование штатных субагентов Codex и независимой оценки при необходимости.
- Предложения проектных skills на основе повторяющейся работы.
- Приёмка по наблюдаемым результатам и сравнение с обычным Codex без Mamkin 2.0.

В продукт не входят и не планируются:

- Другие агентные среды и переносимость между ними.
- Собственный runtime, сервер, UI, планировщик и фоновое выполнение.
- Внешние трекеры и синхронизация с ними.
- Управление портфелем репозиториев и межрепозиторная оркестрация.
- Автоматическое обновление установленных копий и миграция Mamkin 1.x.
- Постоянные специализированные роли, их иерархия и обязательные передачи работы.
- Собственная система выбора моделей и reasoning profiles.
- Обязательные spec, walkthrough, role card и handoff packet для каждой задачи.
- Автоматическое создание или изменение skills и инструкций.
- Обязательные новые hooks, реестры, метаданные версий и CLI.

## Рабочий цикл

1. Прочитать актуальный контекст проекта и состояние работы.
2. Сопоставить запись с исходниками, Git и текущими решениями пользователя.
3. Выбрать доступную задачу.
4. Уточнить только неопределённость, существенно влияющую на результат, полномочия или безопасность.
5. Выполнить работу с нужными skills и инструментами.
6. Проверить критерии готовности.
7. Обновить состояние и кратко сообщить результат.
8. Продолжить, только если разрешённый объём работы это допускает.

Размер плана и документации соразмерен задаче. Небольшое исправление может иметь описание и критерий проверки в одной карточке. Подробная спецификация создаётся, когда без неё трудно договориться о результате или безопасно продолжить.

Коррекции пользователя направляют текущую работу. Исходная цель сохраняется, пока пользователь её не отменил или явно не заменил. Новые соседние задачи записываются в бэклог и не расширяют активную задачу автоматически.

## Модель задачи

| Поле | Требование |
| --- | --- |
| ID | Устойчивый идентификатор внутри проекта |
| Результат | Наблюдаемое изменение и его назначение |
| Критерии готовности | Условия, по которым можно проверить результат |
| Статус | `queued`, `active`, `blocked` или `done` |
| Этап, зависимости, приоритет | Указываются, когда влияют на выбор работы |
| Подробные требования | Ссылка на отдельный spec при необходимости |
| Блокер | Для `blocked`: причина и необходимое действие или решение |
| Результат и проверка | Для `done`: что изменилось, где результат, как проверено и какие ограничения остались |

В `queued` можно сохранить ещё не проработанную идею. Перед началом агент делает её описание достаточно определённым. Существенный выбор остаётся за пользователем; обычные детали реализации агент решает самостоятельно в рамках задачи.

Задача доступна, когда результат понятен, зависимости завершены, текущий этап разрешает её выполнение и работа входит в выданные полномочия. Неизвестная зависимость или цикл зависимостей требуют исправления плана; угадывать порядок нельзя.

При переходе к реализации статус становится `active`. Невозможность продолжить обязательную часть даёт `blocked`. После выполнения критериев и проверки — `done`. Последующие изменения, нарушившие готовность, требуют явно вернуть задачу в работу.

У задачи один источник текущего статуса. Если требования вынесены в отдельный spec, карточка содержит ссылку, а не дублирует их.

## Режимы выбора работы

| Режим | Правило |
| --- | --- |
| `backlog` | Первая доступная задача по заданному приоритету; при равенстве или отсутствии приоритета — по порядку в списке |
| `sequential` | Работа в текущем этапе; задачи внутри него идут в указанном порядке. Заблокированную обязательную задачу нельзя молча пропустить |
| `hybrid` | Этапы идут последовательно, внутри текущего этапа действует выбор из бэклога |

Этап содержит цель, условия завершения и связанные задачи. Необязательные задачи помечаются явно. Переход допускается после завершения обязательных задач и выполнения условий этапа. Если этап требует решения пользователя, одного агентного отчёта недостаточно.

При блокере в `backlog` или `hybrid` можно взять другую независимую доступную задачу в пределах разрешённого объёма. В `hybrid` нельзя переходить за границу текущего этапа.

Агент может предложить изменить приоритеты, этапы или зависимости, но не меняет их самовольно. Внутренний способ решения выбранной задачи он определяет самостоятельно.

## Полномочия и остановка

По умолчанию один запуск выполняет одну задачу. Пользователь может явно разрешить завершить текущий этап или разбирать очередь доступных задач.

| Объём | Граница продолжения |
| --- | --- |
| Одна задача | Завершение выбранной задачи либо блокер |
| Текущий этап | Завершение этапа либо отсутствие доступной работы внутри него |
| Очередь | Отсутствие доступных разрешённых задач либо заданный предел |

Объём работы и известные ограничения сохраняются рядом с активной работой. Новые указания пользователя имеют приоритет. Разрешение продолжать очередь не даёт права на новые расходы, публикацию, production или расширение продуктового объёма.

Агент останавливает зависимую работу перед неразрешённым внешним действием, существенным продуктовым выбором, конфликтом владения изменениями, недоступной обязательной проверкой или при противоречии требований. Он сохраняет выполненную часть и точный следующий необходимый шаг.

Уже выданное разрешение используется повторно, пока его условия не изменились. Правила проекта и среды исполнения продолжают действовать. Нельзя ослаблять ограничения Codex ради выполнения очереди.

Можно задать предел по числу задач или времени. Агентные инструкции о пределах не считаются гарантированным ограничителем расходов; жёсткие ограничения применяются средствами Codex, когда доступны.

## Структура файлов в целевом проекте

```text
AGENTS.md
docs/
  mamkin/
    project.md
    work.md
.agents/
  skills/
    mamkin-setup/
      SKILL.md
    mamkin-work/
      SKILL.md
```

| Файл | Ответственность |
| --- | --- |
| `AGENTS.md` | Команды проекта, устойчивые ограничения, ссылки на контекст и skills |
| `docs/mamkin/project.md` | Цель, существенные ограничения, ссылки на источники и долговременные решения с причинами |
| `docs/mamkin/work.md` | Режим и объём продолжения, этапы, задачи, активная работа, блокеры и результаты |
| `.agents/skills/mamkin-setup/SKILL.md` | Процедура настройки |
| `.agents/skills/mamkin-work/SKILL.md` | Процедура выполнения и продолжения |

Это структура будущего продукта; сохранение спецификации не создаёт эти файлы.

В существующем проекте сохраняются пользовательские инструкции, изменения и подходящие владельцы информации. Mamkin использует ссылки на существующие источники вместо обязательного переноса или копирования. Настройка не запускает продуктовую реализацию и не меняет remotes, внешние настройки или полномочия.

Допускаются только необходимые дополнительные материалы:

- `docs/mamkin/specs/<task-id>.md` — подробные требования.
- `docs/mamkin/runbooks/<procedure>.md` — воспроизводимая процедура.
- `.agents/skills/<project-workflow>/SKILL.md` — отдельно заказанный проектный skill.

## Skills

### mamkin-setup

Триггер: пользователь просит подключить Mamkin 2.0 к новому или существующему проекту.

Входы: текущий репозиторий, задача пользователя, существующие инструкции и проектные источники.

Действия: изучить состояние, найти команды проверки, запросить только недостающие существенные сведения, подготовить минимальный контекст и состояние работы в разрешённых границах.

Результат: проект готов к выбору первой задачи; неизвестные команды и необходимые решения названы явно.

Повторный запуск сохраняет данные, не дублирует записи и дополняет только недостающее. Отсутствующие команды нельзя изобретать или автоматически компенсировать установкой tooling.

### mamkin-work

Триггер: пользователь просит выполнить задачу, продолжить работу или пройти разрешённую очередь.

Входы: задача или объём продолжения, контекст проекта, текущее состояние и исходники.

Действия: выполнить рабочий цикл, восстановить работу при необходимости, выбрать подходящие проверки и сохранить результат.

Результат: завершённая задача или конкретный блокер, актуальное состояние и следующий разрешённый шаг.

Начало и продолжение используют один skill. Для завершения обычной задачи отдельные reset, review и handoff skills не требуются.

Skills описывают триггер, входы, процедуру, результат и условия остановки. Дополнительные references и scripts добавляются только при подтверждённой необходимости, без второго обязательного manual.

## Делегирование и проверка

Основной агент использует штатные субагенты Codex, когда независимое исследование или ограниченная параллельная часть дают практический выигрыш. Сам факт наличия роли не является основанием делегировать.

Задание на делегирование определяет результат, границы владения, необходимые источники, способ проверки и возврат родителю. Одновременные изменения требуют изоляции либо явно непересекающегося владения файлами. Родитель отвечает за итог и интеграцию результата.

Независимая оценка нужна при существенном риске, недостаточности автоматических проверок или необходимости субъективного суждения. Её выполняет другой агент или человек. Если такая оценка обязательна и недоступна, готовность не объявляется.

Проверки выбираются по критериям задачи. Нельзя требовать одинаковый комплект тестов для любого изменения, придумывать отсутствующие команды или повторять достаточные прошедшие проверки без новых оснований.

`done` означает выполнение условий конкретной задачи. Публикация, merge и deployment входят в готовность только при явном включении в задачу и наличии полномочий. Невыполненная обязательная проверка оставляет задачу незавершённой. Альтернативная проверка допустима только при подтверждении тех же критериев.

## Продолжение работы

Перед существенной передачей или остановкой сохраняются активная задача, выполненная часть, проверка, блокер и следующий шаг. Запись обновляется при значимых переходах; полная стенограмма действий не нужна.

Новый запуск читает эти сведения и сверяет их с текущими файлами, Git и решениями пользователя. Старый отчёт не доказывает состояние изменившихся файлов. Проверки относятся к названному состоянию результата; затронутые последующими изменениями проверки повторяются.

Отсутствие или противоречивость записи требует ограниченного восстановления по исходникам и уточнения существенного неизвестного. Нельзя объявлять задачу выполненной по сохранённому статусу без сопоставления с результатом.

## Проектное обучение

Повторяющаяся процедура, одинаковые коррекции пользователя или неоднократное восстановление одних сведений дают повод предложить переиспользуемое решение.

Агент выбирает одну подходящую поверхность: существующий источник, существующий skill, новый проектный skill либо детерминированную проверку. Предложение объясняет конкретное повторение, триггер, ожидаемый результат и экономию работы.

Предложение не блокирует текущую задачу. Создание или изменение skill выполняется отдельно по явному запросу. Проектные знания не передаются в общий фреймворк автоматически.

## Приёмка продукта

Готовность определяется сценариями и сравнением из [плана MVP](mamkin-2-mvp-plan.md#сценарии-приёмки). Проверяется результат, соблюдение полномочий, сохранение пользовательских изменений и возможность продолжения.

Точная формулировка ответов, порядок полей отчёта и число документов не являются критериями качества. Сокращение текста само по себе не доказывает улучшение. Каждый дополнительный механизм должен иметь наблюдаемую пользу относительно обычного Codex без Mamkin 2.0.
