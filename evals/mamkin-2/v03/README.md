# Mamkin 2.0 v0.3 functional evaluation

For the [0.3 contract](../../../docs/project/mamkin-2-spec.md), [M01–M11](../../../docs/project/mamkin-2-mvp-plan.md#сценарии-приёмки) and [implementation scope](../../../docs/project/mamkin-2-v03-implementation.md). No new product runtime or fixtures are installed in user projects.

Freeze sources/criteria before native model calls. `run.py --output /private/tmp/<new-path>` verifies source closure and executes V01–V20 in fresh ephemeral native CLI threads at the existing `gpt-6.1-sol/high`, workspace-write/on-request. No history, resume/fork or prior replies are supplied. Each group carries only actual project text files; no operator edits occur between calls in a group.

V01–V03: readonly plan selection, authorized priority/idea update without execution, fresh query. V04–V09: record accepted choice/reason/rejected option/revisit condition, recall in a new chat, distinguish proposal from approval, explicit supersession preserving old reason, recall both choices, changed facts without fabricated approval. V10–V11: unknown historical reason and conflicting choices. V12–V14: existing active task without ID, actual draft/pause, narrower grant and fresh continuation without reviving the queue. V15–V16: one-off answer/edit without task cards or state churn. V17–V18: setup preserves existing source owners/history and repeat setup is byte-identical. V19–V20: duplicate IDs and contradictory strict order.

Mechanical checks inspect authorized changed paths, exact inert artifacts/journal, preserved dirty data/skills, readonly equality and setup owner preservation. Semantic choices, reasons, rejected alternatives, supersession, unknowns, stable IDs, permission state and routing are judged separately from actual snapshots, final responses and command/file events. No regex/heading/word matcher issues a behavioral pass. A deterministic pass alone never establishes acceptance. Wrong-owner writes, extra ADRs/registries/skills/cards/artifacts or changed code are rejected. Only setup and plan/decision/one-off paths named by each request may change.

Before model calls, control tests must reject readonly mutation, forbidden artifact/code edits and preservation damage, and accept an authorized decision-source change or exact one-off typo. These are harness controls, not evidence of model behavior.

Affected regressions use unchanged `stage-2/run.py` (18 cases: modes, availability, phase gates, authorization, caps/deadline, local preparation) and `stage-2/regression.py` (eight Stage-1 cases with existing semantic test-coverage oracle: setup, actual pause/new chat, required checks). They are fresh runs on the new skills, not inherited passes. Model-edited code in that legacy sequence is checked in the native read-only/network-disabled sandbox. New v0.3 checks only read inert data and execute no model-authored code in the parent.

Retain original failures without rescoring, source/input hashes, actual replies, lossless deduplicated before/after snapshots, meaningful command order and available usage. Keep raw streams temporary. One sample per case, synthetic projects and normal unobservable CLI injected context are limitations. This is functional acceptance, not the same-data comparative usefulness test or deferred real-project pilot. Earlier A10/A15 remain historical; there is no mandatory skill-proposal/delegation retest in the v0.3 core.

## Focused stale-source regression

`stale.py --output /private/tmp/<new-path>` reuses unchanged Stage-0 B04 inputs/request and the existing shared semantic scorer to check a done record contradicted by current source. Unlike the data-only V cases, model-edited Python is checked inside the explicit read-only/network-disabled native sandbox. This focused v0.3 run also reviews assignment of an ID to the admitted existing anonymous managed task. Freeze this supplemental wrapper before its call; retain it separately from the original V01–V20 sequence. Product skills remain unchanged. This is one functional regression, not a repeated efficiency comparison.
